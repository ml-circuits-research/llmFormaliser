The batching advantage

For ten compatible tasks, begin sends one combined model request. Each returned result is assigned to its own task. Ten local conversions then run on ten separate states. Ready judge phases batch again. Ten individual finish phases validate and persist their own results. The caller enqueues full tasks once and calls flush once; it does not reconstruct this workflow with separate API loops.

The worker test with ten independent inputs asserts exactly two fake model calls and forty phase executions. Different prompt prefixes, response arrival times, model errors or configured batch limits can create additional batches. Local state is never shared.

All six workflow files are listed in the README.

Task files

Markdown uses level-two headings for phases and level-three headings for every field. Prompt and JavaScript blocks are literal, without JSON string escapes.

  • formalise_event-judge.md

These baseline files contain begin, toCnl, judge and finish. Each dialect also has a selective-repair and symbolic-first workflow; all six use the same canonical dialect and judge files.

Canonical prompt files

Every generation and repair phase includes the same dialect file: lib/prompts/clause-sop.txt or lib/prompts/event-sop.txt. Includes use ${{lib/prompts/clause-sop.txt}} and expand before batching. Only the final input argument is variable. Scalars can be written as ### tier:small or ###next:repair. Experiment snapshots freeze and hash included files.

Execution policy belongs in configuration

pworker.config.json keeps cache enabled and the selected model fixed. No maxTokens or temperature is imposed. Task types contain phase logic, tier and batching declarations. Local phases contain explicit code with library imports, conversion calls, pair construction and result writes. Libraries execute in the worker sandbox; codeFile is forbidden.
